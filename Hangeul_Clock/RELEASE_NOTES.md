### 🔁 Chinese_Clock 실기에서 확인된 결함 6건 전파 (언어 중립)
중국어판을 만들며 실기에서 드러난 결함 중 **한글판에도 그대로 있는 것**을 소스로 대조해 확인하고
고쳤습니다(중국어판 `PLAN.md` §📌). 그중 A-2 는 **원인 4개가 한 세트**라 하나만 고치면 화면이
그대로입니다 — 넷을 함께 고쳤습니다(중국어판은 세 번에 나눠 고쳤습니다).

### 🐛 A-1 · 웹페이지가 **백지**로 뜬다
- **증상**: 시리얼에는 `[WEB] WebManager started` 가 정상으로 찍히고 크래시도 없는데 브라우저에는 아무것도 안 뜹니다.
- **원인**: `handleRoot()` 가 `server.send()` 로 PROGMEM 페이지를 보냈습니다. ESP32 WebServer 코어의 `send(int, const char*, const char*)` 는 첫 줄에서 `const String passStr = (String)content;` 로 **전체 페이지를 힙에 복사**합니다(코어도 "Use send_P for long arrays" 라고 경고합니다). 이 기기는 I2C 버퍼 4장을 상시 점유하므로 연속 40~70 KB 할당이 실패하기 쉽고, 그러면 서버는 정상인데 응답만 씻겨 나갑니다 — **크래시도 로그도 없어** 가장 진단이 어려운 부류입니다.
- **수정**: `server.send_P(200, PSTR("text/html"), font_studio_html)` — `strlen_P()` 로 길이만 재고 스트림으로 내보내므로 복사가 없습니다.

### 🐛 A-2 · 폰트를 올렸는데 드롭다운이 "Empty Slot" 이다 (원인 4개)
- **① 이름이 업로드와 다른 요청으로, 그것도 조건부로 갔습니다.** 이름은 업로드가 끝난 뒤 별도 `/api/config` POST 로만 전달됐고 `if (els.fIn.files[0])` 조건부였습니다. 그 요청이 빠지거나(폰트 미선택) 늦으면 슬롯에는 글리프만 남습니다.
  → 이름도 슬롯과 같은 이유로 **시작 시점에 한 번만 읽어 고정**하고, 글리프를 보내는 **같은 요청**(`POST /upload?slot=N&font=<파일명>`)에 실어 보냅니다. 폰트 미선택이면 업로드를 시작하지 않고 이유를 띄웁니다 — 조용히 빈 슬롯을 만들지 않습니다. 한글 파일명은 UTF-8 다바이트이므로 `encodeURIComponent` 로 싣습니다.
- **② 슬롯을 업로드마다 다시 읽었습니다.** `?slot=${els.slot.value}` 를 40회 각각 읽어, 도중에 값이 흔들리면 도착점이 달라집니다. → `const targetSlot` 으로 고정.
- **③ 이름표를 "업로드한 슬롯"이 아니라 "현재 슬롯"에 썼습니다.** `setFontName()` 은 `configManager.font_slot` 에 씁니다.
  → **`setSlotName(slot, name)` 신설**(파일·캐시·현재 슬롯이면 config까지) 후 `setFontName()` 은 위임만 하게 했습니다. 업로드 경로는 `setSlotName()` 만 씁니다.
- **④ 32바이트 상한이 실제 폰트 이름을 조용히 거부했습니다.** 옛 `name.length() >= 32`(실질 31바이트)의 근거 주석은 "이름을 `/fN/name.txt` 파일명으로도 쓴다" 였는데 **사실이 아닙니다** — 경로는 리터럴이고 이름은 그 파일의 **내용**으로만 들어갑니다. 라이선스 접미사가 붙으면 이름은 금방 31바이트를 넘습니다.
  → `config.h` 의 **`FONT_NAME_MAX_LEN 64`** 한 곳으로 옮겼습니다(늘리려면 그 한 곳만).

### 🐛 A-3 · 슬롯을 바꿔도 `/api/config` 의 `slot_names` 가 부팅 시점 값이다
`setFontSlot()` 이 `configManager.font_name` 만 갱신하고 `_slotNames[slot]` 는 건드리지 않았습니다. → 두 값을 **같은 문자열에서 함께** 씁니다.

### 🐛 A-4 · 빈 슬롯 표기가 두 갈래
부팅 캐시는 `"Empty"`, `setFontSlot()` 은 `"Empty Slot"` 이었습니다. 같은 상태가 두 이름으로 보입니다. → **`"Empty Slot"` 로 통일**.

### 🐛 A-5 · 본문 없는 POST 에 아무 응답도 없다
`handleSetConfig()` 이 `hasArg("plain")` 가 거짓이면 **아무것도 보내지 않았습니다.** ESP32 WebServer 는 빈 응답을 돌려주고 웹의 `fetch()` 는 그것을 "응답 없음"으로 보고 저장 실패처럼 표시합니다. → **`400 Missing body`** 로 명시적 거절.

### 🐛 B-1 · 슬롯을 바꿔도 "업로드됨" 배지가 이전 슬롯 것을 물려받는다
배지 상태는 **슬롯마다 다른 사실**인데 배지 DOM 은 하나뿐입니다. → `clearInventoryState()` 를 두고 `els.slot` 에 **전용 핸들러**(저장 + 배지 초기화)를 붙였습니다. 이 판은 `CONFIG_FIELDS` 없이 `[els.anim, …]` 배열로 일괄 바인딩하므로, **그 배열에서 `els.slot` 을 빼야** 전용 핸들러가 덮어써지지 않습니다(중국어판이 이 함정을 §12.7 결함 A 로 밟았습니다).

### 🔧 C · 실패가 침묵하지 않게 (진단)
- 업로드 START 에서 `[WEB] upload start slot=%d fontArg=%d font='%s'` 를 **무조건** 찍습니다. `fontArg=0` 이면 서버가 못 본 것, `1` 인데 이름표가 안 붙으면 그 뒤 단계의 문제입니다.

## [v2.9.1] ✅ 커밋완료 - 2026-10-04
### 🔍 제로베이스 코드 리뷰 반영
코드만 읽고(기존 문서·메모리 제외) 처음부터 리뷰한 결과를 조치했습니다. 사용자-visible 동작이 바뀌는 수정은 별도로 표시합니다.

### 🐛 1자 텍스트가 화면 밖으로 나가던 버그 수정 (P0)
- **증상**: 글자가 **1개뿐인 화면**(예: `AM`, `PM`)이 가운데 정렬되지 않고 화면 오른쪽 밖으로 나가 보이지 않았습니다.
- **원인**: `Renderer::getCharData()`의 좌표식이 `if (centered || count == 1)`과 `else` 두 갈래를 탔습니다. `else` 갈래는 마지막 글자를 계산과 무관하게 `RIGHT_COL_X`(96)에 고정했는데, `count == 1`이면 그 글자가 **동시에 `j == 0`이면서 "마지막"**이므로 가운데 정렬(`startX = 48`)을 무시하고 `x = 96`에 놓였습니다.
- **수정**: 배치 계산을 순수 모듈 `renderer_layout.cpp`의 `layoutCharX()`로 분리하고, `count == 1`을 가운데 정렬 갈래에 명시적으로 포함시켰습니다. `count >= 2`의 반환값은 원본과 **픽셀 단위로 동일**합니다(회귀 테스트로 확인).
- **부수 수정**: `LAYOUT_MAX_CHARS`가 8이었으나, `HangeulTimeConverter`가 만들 수 있는 문자열을 24×60×60 전수 조합으로 확인한 결과 실제 최대는 **4자**(`이십일초`)입니다. 128px ÷ 32px 칸 = 4칸이 화면 전체이므로 4로 내렸습니다. 과대하게 잡혀 있으면 5자 이상에서 화면 밖 좌표가 조용히 계산됩니다.

### 🐛 부분 저장이 조용한 데이터 손실을 만들던 문제 수정
- **원인**: `ConfigManager::saveNow()`가 시간대 검증에 실패하면 **tz만 건너뛰고 나머지 10개 필드는 그대로 썼습니다.** 사용자는 "설정이 저장됐다"는 로그만 보고 재부팅하면, 바뀐 값 중 일부만 반영된 상태를 만납니다.
- **수정**: 검증 실패 시 **전체를 건너뛰도록** 바꿨습니다. 조용한 부분 저장으로 인한 데이터 손실을 막습니다. `_isDirty`는 유지되므로 다음 `setDirty()`에서 재시도됩니다.

### 🐛 4바이트 UTF-8 문자를 3바이트로 오판정하던 버그 수정
- **원인**: 리딩 바이트 판정에서 하위 3비트만 검사해, 4바이트 문자(U+10000 블록, 이모티콘·고대 문자)의 길이를 3으로 잘못 계산했습니다. 이어지는 바이트가 문자열 경계를 넘어 읽혔습니다.

## [v2.9.0] — 2026-10-02
### ✂️ 분할 플랩 애니메이션 모드 추가 (Split Flap)
- **새 모드 7**: 공항 출발 안내판(Solari)처럼 글자를 **상하 2등분**해 순서대로 접으며 바꿉니다. 위쪽 절반이 가운데선을 축으로 접혀 수평으로 눕고, 그 자리에 새 글자의 위쪽 절반이 펼쳐집니다. 이어 아래쪽 절반이 같은 방식으로 접힙니다.
- **축 투영(hinge projection)**: 축에서 거리 `d`인 행이 축에 `d·cosθ`만큼 가까운 곳에 투영됩니다. 목표 높이를 `h = 32·cosθ`로 두면 원본 행은 `srcTop(y,h) = 31 - ((31-y)*32)/h`, `srcBottom(y,h) = 32 + ((y-32)*32)/h`가 됩니다. 단순 압축(`src = y-(32-h)`)은 `h→0`일 때 글자 **아래**쪽이 축에 남아 **위에서 잘려나가는 wipe**로 보이므로 채택하지 않았습니다. 축 투영은 `h→0`에서 자유 가장자리(원본 행 0/63)가 축으로 밀려와 마지막에 사라져 실제 플랩과 같은 운동입니다.
- **연속성 보장**: `h == 32`에서 위 식은 정확히 `src == y`가 됩니다. 그래서 **모드 진입 첫 프레임과 종료 마지막 프레임이 정적 렌더링과 픽셀 단위로 동일**합니다(불변식 I1로 검증). 애니메이션이 붙었다 떼는 느낌이 나지 않습니다.
- **XOR 모드 상쇄 회피**: 디스플레이가 `setBitmapMode(1)`이므로 `drawBitmap`은 겹치는 픽셀을 **지웁니다**(눈 조립 모드와 정반대). 그래서 위쪽 두 밴드를 `[0, 32-h)`와 `[32-h, 32)`, 아래쪽 두 밴드를 `[32, 32+h)`와 `[32+h, 64)`로 배치해 **y 구간이 겹치지 않게** 설계했습니다. 어느 목표 행도 2회 이상 그려지지 않음이 불변식 I3으로 확인됩니다.
- **고아 열 처리**: 글자 수가 바뀌는 전환("십" → "이십", 정각 화면 등)에서 짝이 없는 열이 생깁니다. `drawFlapChar(old, new, ...)` **한 번**에 옛·새를 함께 접도록 만들어, 새 글자가 없는 열은 빈 문자열을 넘겨("") 접어 닫으면 되도록 했습니다. 기존 글자 단위 전환 경로는 옛 글자와 새 글자를 분리해 그려 플랩의 동시 접힘을 표현할 수 없었습니다.
- **프레임 예산 재사용**: 새 상수를 추가하지 않고 `ANIMATION_STEPS_DEFAULT`(16) × `ANIMATION_STEP_DELAY_MS`(10ms)를 그대로 씁니다. `updateTick`/`updateAll`의 모드별 분기를 건드리지 않기 때문입니다. 실효 주기는 `max(10ms, 렌더+I2C)` ≈ 25~45ms로 총 0.4~0.7초, 1초 갱신 주기 안에 들어옵니다.
- **부동소수점·난수 미사용**: 접힘은 정수 나눗셈만으로 재현합니다. ESP32-C3의 프레임 비용과 호스트 테스트 결정성을 함께 만족합니다.
- **구조**: 기하는 `renderer.cpp`의 파일 지역 `static` 함수로(`FlapSource`/`flapTopSrcRow`/`flapBottomSrcRow`/`drawTopFold`/`drawBottomFold`) 두고, 공개 API는 조합 함수 `Renderer::drawFlapChar` 하나만 노출합니다. 오케스트레이션은 `DisplayManager::renderFlapFrame`. 커스텀 비트맵이 없는 글자는 눈 조립 모드와 같은 관례로 `progress` 절반을 경계로 `drawSingleChar` 폴백합니다.

### 🐛 분할 플랩: 고아 열 애니메이션 누락 버그 수정
- **증상**: 글자 수가 바뀌는 전환(예: `이십구초` → `삼십초`, `삼십초` → `삽십일초`)에서 글자가 **접히지 않고 그냥 바뀐다**. 같은 글자 수를 유지하는 전환은 잘 된다.
- **원인 ① — 좌표가 글자 수에 의존**: `Renderer::getCharData`의 우측 정렬 좌표가 글자 수마다 전부 달라집니다(`startX = (96 - (count-1)*32) / 2`). `count=4` → x `[0,32,64,96]`, `count=3` → x `[16,48,96]`. 애니메이션은 `findOldIndexAtX`로 **같은 x**에 있는 옛 글자·새 글자를 짝지으므로, 글자 수가 바뀌면 **마지막 열(`x=96`)만 겹칩니다**. 그마저 초 화면은 `초`가 그대로여서 아무것도 접히지 않습니다. 사용자가 관찰한 "같은 위치에서만 애니메이션"은 정확히 이 동작입니다.
- **원인 ② — 빈 글자를 비트맵 부재로 오인**: 고아 열은 `drawFlapChar(old, "")` 또는 `("", new)`로 호출되는데, 펌웨어가 빈 문자열과 "커스텀 비트맵이 없는 글자"를 구분하지 않고 **동일하게** 취급해 정적 폴백(진행도 128에서 하드 컷)으로 보냈습니다. 즉 접힘 기하에 들어가지 못하고 `progress=128`에서 순간적으로 사라지거나 나타나 있었습니다.
- **수정**: 둘을 분리했습니다. **빈 문자열은 "이 열에 글자가 없다"는 뜻**이므로 `data == nullptr`(전부 0인 비트맵과 동등)로 접힘 기하에 그대로 넘깁니다. `drawTopFold`/`drawBottomFold`는 이미 `data`가 nullptr인 쪽을 건너뛰도록 작성되어 있어 **기하 수식은 한 줄도 바뀌지 않았습니다.** 커스텀 비트맵이 없는 실제 글자에만 정적 폴백을 남겼습니다. 결과적으로 고아 옛 글자 열은 **접혀 닫히고**, 고아 새 글자 열은 **펼쳐져 나타납니다.**
- **웹 미리보기는 이 버그가 없었습니다** — JS는 처음부터 빈 문자열을 `null`로 받아 접힘 기하에 넘기고 있었습니다. 펌웨어만 단독으로 잘못된 경로를 탔습니다.
