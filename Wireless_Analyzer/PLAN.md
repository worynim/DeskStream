## 1. 측정할 수 있는 것 / 없는 것

ESP32-C3는 스펙트럼 분석기가 아니라 **WiFi/BLE 수신기**다. 측정값의 한계를 먼저 정해 둔다.

| 항목 | 방법 | 얻는 값 | 한계 |
|:--|:--|:--|:--|
| AP 목록 | WiFi 스캔 (`WiFi.scanNetworks(async)`) | SSID · BSSID · 채널 · RSSI · 보안 방식 | 비콘을 보내는 AP만 보임. 스캔 1회 약 1.5~2초(액티브) |
| 채널 혼잡도 (추정) | 스캔 결과로 계산 | 채널별 AP 수 · 겹침 가중 신호 합 | "AP가 몇 개 있나"이지 "실제로 얼마나 바쁜가"는 아님 |
| 채널 트래픽 (실측) | 프로미스큐어스 모드로 채널 순회하며 프레임 수 집계 | 채널별 초당 프레임 수 · 평균 RSSI | 각 채널을 잠깐씩만 들음(시분할). 디코딩 가능한 802.11 프레임만 셈 |
| BLE 기기 | BLE 패시브 스캔 | 광고 주소 · RSSI · 제조사 ID · 이름(있으면) | 랜덤 MAC 주기 변경으로 같은 기기가 여러 개로 셀 수 있음 |
| 비-WiFi 간섭 | — | — | 전자레인지·무선 마우스 등 **원시 RF 에너지는 측정 불가** (화면·README에 명시) |

> **라디오 1개 공유**: C3는 WiFi와 BLE가 같은 RF를 시분할로 쓴다. 동시에 돌리면 양쪽 모두 놓치는 패킷이 늘어나므로
> **스캔 스케줄러가 WiFi 스캔 → 트래픽 샘플링 → BLE 스캔을 번갈아** 실행한다 (§3.2).

## 2. 화면 구성 (512x64, 모드 6개)

**Agent_Monitor와 같은 방식**으로 그린다: 화면별 U8g2 버퍼(`display.screen(i)`)에 그리고 `display.push()`로 보낸다.
512px 폭 그래프·글자는 x 좌표 0~511 가상 좌표로 그리되 화면 i에는 x를 `-128*i` 만큼 옮겨 그리고, 화면 밖은 U8g2가 잘라낸다.
단 **사선(`drawLine`)은 음수 x에서 잘못 그려지므로** 화면 범위로 먼저 잘라 그린다 (`canvas512.h`, P0 `drawLine512()`).
글꼴은 Agent_Monitor의 **갈무리7(`u8g2_font_galmuri7_kr`) 하나만** 쓴다 (`drawUTF8`, 다른 글꼴 사용 안 함).
채널 간격은 32px, 채널 c의 중심 x = 32c + 48 (1 = 80, 13 = 464). 채널 중심을 화면 경계(128·256·384)에서 16px 이상 떼어
채널 번호가 두 화면에 쪼개지지 않게 한다 (P1에서 32(c+1)로 두었더니 3·7·11이 경계에 걸림).

| # | 모드 | 내용 |
|:--|:--|:--|
| 1 | **채널 스펙트럼** | AP마다 폭 4채널(20MHz)짜리 언덕(사다리꼴/포물선)을 RSSI 높이로 겹쳐 그림. 가장 센 몇 개는 꼭대기에 SSID 약자 표시. 하단에 채널 번호 축 |
| 2 | **채널 혼잡도 막대** | 채널마다 왼쪽 = 그 채널에 둘 때의 비용 막대(§3.3), 오른쪽 = 실측 활동량 막대(속 빈, 0~400프레임/s, §3.5). 막대 위 같은 채널 AP 수(0 포함). **추천 채널**(§3.3) 반전 + 왼쪽 위에 이유(같은 채널·겹침 AP 수, 활동량) |
| 3 | **AP 목록 + 추이** | RSSI 순 AP를 한 줄씩(6줄): SSID · 채널 · 현재 RSSI · 최근 60회 RSSI 스파크라인(줄마다 최소~최대로 확대, 최소 10dB 폭). 커서(선택 AP)를 BTN3/4로 옮기면 스크롤 |
| 4 | **AP 추적 (선택 AP)** | 목록에서 고른 AP 하나: 화면 1에 SSID·채널·현재 RSSI(갈무리7 굵게 — 다른 글꼴 안 씀)·세기 막대·최고/평균, x 132~511에 최근 190회 RSSI 그래프. 그 AP의 **채널만 반복 스캔**(약 0.15초 간격). 옵션으로 **부저가 신호가 셀수록 빠르게 삑삑**(기본 꺼짐, BTN3 길게) |
| 5 | **BLE 기기** | 화면 1: 기기 수(굵게) + 거리 구간별 개수(가까움 > −60 / 중간 / 멂 < −80dBm), 화면 2: 기기 수 추이(최근 60회), 화면 3·4: 센 순서 6줄 — 이름 · 제조사 · RSSI (주소는 표시 안 함). **이 화면에서만 BLE 스캔** |
| 6 | **요약** | 화면 4개를 타일로: ① WiFi AP 수·사용 채널 수 ② 추천 채널·가장 혼잡한 채널(`busiestChannel`) ③ 가장 센 AP(SSID·채널·RSSI) ④ BLE 기기 수·거리 구간. 이 화면에서는 WiFi 스캔 → 채널 순회 → BLE 스캔을 모두 돈다 (한 바퀴 약 7초) |

모드를 바꾸면(부팅 직후 포함) 화면 2(x 128~255) 가운데에 `2/4 채널 혼잡도`처럼 모드 이름을 1.5초 띄운다
(512px 가운데 x 256은 화면 경계라 글자가 쪼개지므로 화면 하나 안에 둔다).

## 3. 소프트웨어 구조

### 3.1 파일 구성 (P1까지 구현된 것 ✅, 나머지 예정)

```
Wireless_Analyzer/
├── Wireless_Analyzer.ino   # ✅ setup/loop, 버튼, 모드 전환, AP 선택·추적 부저, 시리얼 디버그(d = 화면 덤프, m = 다음 모드, n = 다음 AP)
├── config.h                # ✅ 버전, 스캔 주기, 히스토리 길이 등 상수
├── wifi_scan.cpp/.h        # ✅ 비동기 AP 스캔 → ApTable 갱신
├── wifi_sniff.cpp/.h       # ✅ 프로미스큐어스 채널 순회, 채널별 제어·데이터 프레임 수 집계
├── ble_scan.cpp/.h         # ✅ NimBLE 액티브 스캔(이름 받으려고) → BleTable 갱신
├── ble_table.cpp/.h        # ✅ 순수 로직: BLE 기기 테이블(주소로 중복 제거, 30초 유지), 거리 구간, 제조사 이름
├── scheduler.cpp/.h        # ✅ 라디오 시분할 스케줄러 — WiFi 스캔 → (혼잡도 모드면) 순회 → (BLE 화면이면 WiFi 대신) BLE 스캔
├── traffic.cpp/.h          # ✅ 순수 로직: 채널 활동량(초당 프레임) 지수 평균
├── analysis.cpp/.h         # ✅ 순수 로직: AP 테이블·RSSI 히스토리 링버퍼, 채널 비용, 추천 채널, 부저 간격, 직선 자르기 (+ BLE 중복 제거 예정)
├── canvas512.h             # ✅ 4화면을 512x64 한 장처럼 그리는 도우미 (글자·직선·가로선·상자)
├── ui.cpp/.h               # ✅ 모드별 렌더러 (스펙트럼·막대·목록·추적 → BLE·요약 추가 예정)
├── u8g2_font_galmuri7_kr.h # ✅ Agent_Monitor와 같은 갈무리7 한글 글꼴 (U8G2_USE_LARGE_FONTS 필요)
├── test/                   # ✅ analysis 호스트 단위 테스트 (네이티브 C++)
├── PLAN.md · README.md · RELEASE_NOTES.md
└── partitions.csv          # ✅ DeskStream 공통 파티션 (WiFi+BLE로 1.25MB 초과 예상)
```

- 화면·버튼·부저·설정 저장은 **`DeskStreamCore`** 를 쓴다 ([AI_GUIDE.md](../AI_GUIDE.md) 규칙). 공유기 접속이 없으므로
  `WifiService`/`TimeSync`/`WebConfigApi`는 쓰지 않는다.
- 측정·계산(`analysis`)은 하드웨어 의존 없는 순수 함수로 분리해 호스트에서 테스트한다.

### 3.2 라디오 스케줄러

```
┌─▶ WIFI_SCAN (액티브, 채널 1~13, ~2s) ──▶ SNIFF (채널당 ~150ms × 13, 선택) ──▶ BLE_SCAN (~3s) ─┐
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

- 한 주기 약 5~7초. 각 단계 시간은 `config.h` 상수, P0에서 실측 후 확정.
- (P3 구현) 순회(SNIFF)는 **혼잡도 모드에서만** 넣는다 — 활동량을 보여주는 화면이 거기뿐이라, 다른 모드는 스캔 주기(2.3초)를 그대로 둔다.
  혼잡도 모드 한 주기 = 스캔 2.3초 + 순회 약 2초. 모드를 벗어나거나 일시정지하면 순회를 바로 멈춘다.
- 모드에 따라 비중 조정: AP 추적 모드에서는 **해당 채널만** 짧게 반복 스캔해 갱신 주기를 1초 이하로 줄이고 BLE는 쉼.
  (P2 구현: 채널 하나 스캔 약 0.15초. 그동안 다른 채널 AP는 기록·정리하지 않는다.)
- (P4 구현) BLE 스캔(액티브 3초)은 **BLE 화면에서만**, 그때는 WiFi 스캔을 쉰다 — 다른 화면의 WiFi 갱신 주기를 지키려고 (2026-11-11 결정).
  기기 수 추이는 BLE 화면에 있는 동안만 쌓인다. (P5) 요약 화면은 WiFi 스캔 → 순회 → BLE 스캔을 모두 돌린다 — 기기 수 추이도 이때 쌓인다.
- 국가 코드를 **KR(채널 1~13)** 로 명시 설정한다 (기본값에 따라 12·13 채널이 빠질 수 있음).

### 3.3 채널 비용과 추천 채널 (추정)

그 채널에 공유기를 둔다고 할 때의 비용을 채널 1~13마다 계산한다 (`analysis` `computeChannelStats` — 0.2.1부터).

| 대상 AP | 왜 | 비용 |
|:--|:--|:--|
| 같은 채널, −82dBm 이상 | 서로 신호를 알아듣고 번갈아 보낸다 (CCA) → 시간 나눠 쓰기 | 신호 세기(mW) 그대로 |
| 일부 겹치는 채널(거리 1~4), 또는 같은 채널이지만 −82dBm 미만 | 알아듣지 못하는 잡음 → 충돌로 패킷이 깨짐 | 신호 × 겹침 비율 × **2배**(+3dB) |

- 겹침 비율은 22MHz 폭 신호가 채널 간격 5MHz × 거리만큼 떨어졌을 때 겹치는 비율 (22 − 5d) / 22
  → 거리 0/1/2/3/4 = 1.00/0.77/0.55/0.32/0.09, 5 이상 0 (1·6·11이 서로 안 겹침).
- 비용(dBm) = 10·log10(합). 혼잡도 막대는 이 비용을 −95~−30dBm → 0~36px로 그린다 (막대와 추천 기준이 같다).
- **추천 채널** = 비용 + (1·6·11 밖이면 **3dB 벌점**)이 가장 낮은 채널. 벌점은 1·6·11 밖 채널이 양쪽 이웃 그룹 모두에 잡음을 주기 때문.
  AP가 1·6·11에 몰려 있으면 사이 채널은 양쪽 잡음(2배 가중)을 받아 1·6·11 중에서 추천되고,
  AP가 흩어져 있어 1·6·11 밖이 확실히 한산할 때만 그 채널이 추천된다 (호스트 테스트 `testRecommendGrid/OffGrid`).
- 화면 왼쪽 위에 이유를 쓴다: `추천 ch5 (같은 채널 1 / 겹침 15)`.
- 가중치(2배)·벌점(3dB)·CCA 기준(−82dBm)은 `analysis.h` 상수. 정답이 정해진 값이 아니라 실제 환경을 보며 조정한다.
- 0.2.0까지는 1·6·11 중 겹침 가중 신호 합이 가장 낮은 채널만 추천했다 (같은 채널과 옆 채널을 같은 무게로 계산).
- (P3) 실측 활동량이 있으면 **제어·데이터 100프레임/s마다 +3dB**를 더한다 (`kBusyDbPer100Fps`) — AP 수가 아니라 실제로 얼마나 바쁜가.

### 3.5 채널 활동량 실측 (P3)

- 프로미스큐어스 모드로 채널마다 150ms씩 머물며 받은 **제어·데이터 프레임 수/초**를 센다 (0.3.2부터).
  제어 프레임은 `esp_wifi_set_promiscuous_ctrl_filter`를 따로 켜야 들어온다.
- 비콘 등 관리 프레임은 AP 수에 비례할 뿐 트래픽이 아니라 빼고, 오류 프레임(`rx_state ≠ 0`)은 필드를 믿을 수 없어 뺀다.
  채널을 바꾼 직후 앞 채널 프레임은 `rx_ctrl.channel`로 걸러 버린다.
- 한 번 측정은 흔들리므로 바퀴마다 지수 평균(새 값 30%)으로 섞는다.
- 화면: 활동량 막대는 0~400프레임/s를 0~36px로 (부하 측정 최고 329). 추천: 100프레임/s마다 +3dB (`kBusyDbPer100Fps`).
- 시리얼 `t`로 채널별 활동량·측정 횟수를 출력한다.
- 0.3.0~0.3.1은 프레임마다 속도·길이로 **전송 시간(airtime)** 을 추정해 "사용률(%)"을 냈지만, 아래 부하 측정에서 부하를 거의 반영하지 못해 바꿨다.

#### 부하 측정 결과 (2026-11-11, 0.3.1, ch10 `test_2`에 영상 스트리밍)

| ch10 | 부하 없음 | 부하 중 |
|:--|:--|:--|
| 초당 프레임 | 92 | **329** (3.5배) |
| 추정 사용률 | 5.4% | 5.2~11.8% (거의 그대로) |

임시 진단 스케치로 ch10을 3초씩 들어 본 프레임 구성:
- 제어 프레임 370~732개 중 대부분이 24Mbps·32바이트 = **Block ACK**. 데이터 프레임은 350~391개로 대부분 6Mbps·150바이트 안팎이거나 MCS 0~6·300바이트 안팎.
- **MCS 8~15(공간 스트림 2개) 프레임은 하나도 없다.** ESP32-C3는 안테나·스트림이 1개라 2스트림 프레임을 해독하지 못한다.
  요즘 휴대폰·공유기의 대용량 전송은 대부분 2스트림 집합(A-MPDU)이라, **스트리밍 데이터 본체는 보이지 않고 그 응답(Block ACK)만 보인다.**
- `rx_state` 오류 프레임이 3초에 35~66개 — `rate` 값이 16 이상(정의 밖)이고 길이가 1600바이트를 넘는 등 필드를 믿을 수 없다.
- 결론: 전송 시간 합으로 계산한 사용률은 부하를 거의 반영하지 못한다. 반면 초당 프레임(특히 Block ACK 같은 제어 프레임)은 뚜렷이 늘었다
  → **초당 제어·데이터 프레임(활동량)으로 바꿈** (2026-11-11 결정, 0.3.2).
- 0.3.2 같은 부하 중: **ch10 = 153프레임/s**, 나머지 채널 0~6 (ch11만 48). 관리·오류 프레임을 빼니 평소 채널은 거의 0이 되어 부하 채널이 확연히 드러난다.
- 스트리밍을 끈 뒤 30초: ch10 = 10~66프레임/s(10초 간격 3회)로 내려갔다. 150ms 측정이라 바퀴마다 흔들림이 크다(평균 섞기 후에도 수십 단위).

### 3.6 설정 저장·부팅 화면 (P5)

- `ds::ConfigStore`(NVS 네임스페이스 `wanalyzer`) — 키 `mode`(마지막 모드 0~5) · `bright`(밝기 단계 0~3) · `flip`(뒤집기).
  바꾸면 5초 뒤 저장(그 사이 또 바뀌면 다시 미룸). 웹 설정 API는 쓰지 않는다 (단독 장치, §5 결정 2).
- 추적 부저 켜짐은 저장하지 않는다 (기본 꺼짐 결정 — 켤 때마다 의도적으로).
- 부팅 화면: 화면마다 하나씩 `Wireless` · `Analyzer` · `2.4GHz 무선 / 환경 분석기` · `WiFi / BLE / v버전`, 최소 1.5초.
- 보드 확인: 요약 화면, 뒤집기(`f`) 후 리셋해도 요약 모드·뒤집힘 유지(화면 덤프). 부팅 화면·밝기 단계·BTN1/BTN4 길게는 실기에서 확인.

### 3.4 데이터 크기 (메모리)

| 테이블 | 크기 (안) |
|:--|:--|
| AP: 최대 48개 × (BSSID 6 + SSID 33 + 채널·RSSI·보안 + RSSI 히스토리 60B) | 약 5KB |
| 추적 기록: 190 × 1B | 0.2KB |
| 채널 통계: 13 × (AP 수, 점수, 프레임 수, 히스토리 60) | 약 1KB |
| BLE: 최대 64개 × (주소 6 + RSSI + 제조사 ID + 이름 24 + 마지막 본 시각) + 기기 수 히스토리 60 | 약 2.5KB |
| 화면 버퍼 | DisplayCore 내장 (화면당 1KB × 4) |

- 오래 안 보인 항목은 제거(AP 60초, BLE 30초). BLE 기기 수 = "최근 30초 안에 본 서로 다른 주소 수".
  (휴대폰은 랜덤 주소를 약 15분마다 바꾸므로 30초 창이면 같은 기기를 두 번 셀 일이 드물다.)
- (P4) NimBLE 초기화 후에도 동작 중 힙 여유 확인 — 보드에서 BLE 화면 150초 연속 동작, WiFi 화면 전환 이상 없음.
- 한글 SSID는 갈무리7 글꼴로 표시한다 (§2). 글꼴에 없는 문자는 그려지지 않는다.
