## [v1.1.0] — 2026-11-08

### 🚀 전송 경로 최적화 — 4화면 풀 프레임 40fps → **86.8fps**

**측정 도구 — 부팅 FPS 벤치마크** (`FPS_BENCH_ON_BOOT`, `display.runFpsBenchmark()`)
- 0xAA/0x55를 번갈아 채워 매 프레임 **모든 바이트**를 바꾸고(풀 프레임 강제) `pushParallel()`을 잰다.
- 케이스 A(4화면)·B(1화면) — 동시 전송이 제대로면 둘의 전송 시간과 트랜잭션 수가 같다.
- `writeConcurrent()`가 성공한 트랜잭션의 비트 주기 수·시간을 누적 → **실효 SCL** 산출.
- 결과는 시리얼과 화면 0(8초). 끄면(`0`) 코드가 컴파일되지 않는다 (Flash 99%).
- 원본 `Hangeul_Clock` v2.9.9에도 같은 형식으로 넣어 비교했다.

**첫 측정 — 원본보다 클럭이 낮았다**: 원본 HW 710 / SW 763kHz, 이 펌웨어 **474kHz**.
`BB_HALF_BIT_NS 0`(지연 없음)인데도 비트당 약 340사이클(2.1us)이 들었다 → 병목은 지연이 아니라 코드.

**수정**
1. **니블 LUT** — 바이트마다 돌던 `bbByteBitMasks()`(4버스 × 8비트 이중 루프)를 1KB 표로 대체.
   비트 i의 HIGH 핀 = 표값 4개의 OR (`bbBuildNibbleLut()` / `bbOnesFromLut()`, 순수 함수).
   호스트 테스트로 15조합 × 256값 × 8비트를 기존 함수와 전수 대조 + 복조 왕복.
2. **SCL 상승 대기를 스핀으로** — 풀업 RC 때문에 SCL은 쓰기 직후 대개 아직 LOW다.
   예전 `sclWaitHigh()`는 첫 읽기가 LOW면 곧장 `micros()` 타임아웃 루프로 빠져
   **매 비트** 그 비용을 냈다. 이제 레지스터를 `BB_SCL_SPIN_MAX`(32)번 다시 읽고,
   그래도 LOW일 때만 타임아웃 경로로 간다 (스트레칭·stuck 감지는 그대로).
3. **IRAM + -O2** — `writeConcurrentImpl()`을 `IRAM_ATTR`·`optimize("O2")`로, 바이트 전송은
   인라인 + 8비트 루프 펼침. ACK는 버스별 루프 대신 `(GPIO.in & 참여핀) == 0` 한 번.

**결과 — 클럭이 너무 올라갔다**: 지연 0에서 실효 **1.53MHz**. 1화면은 정상이었지만
4화면에서 패널 하나가 ACK를 놓쳐 동시 재생 실패 → 순차 폴백(트랜잭션 74 → 187/frame),
시계 화면 노이즈, **한 화면만 밝아짐**(밝기 명령 바이트 손상으로 추정).

**클럭 조정** — 이제 오버헤드가 작으니 `BB_HALF_BIT_NS`로 클럭을 직접 고른다.

| `BB_HALF_BIT_NS` | 실효 SCL | 4화면 | FPS | 오류 |
|--:|--:|--:|--:|:--|
| 0 | 1,530 kHz | (폴백) | — | ❌ |
| 250 | 848 kHz | 15.0 ms | 66.6 | 0 |
| **150 (기본)** | **1,170 kHz** | **11.5 ms** | **86.8** | 0 |

⚠ 150은 짧은 부팅 벤치마크(WiFi 켜기 전, 50프레임)로만 확인했다. 장시간·WiFi 동작 중
시리얼에 `동시 재생 실패 -> 순차 폴백`이 보이거나 노이즈가 생기면 200~250으로 올린다.

### 🗑️ 시도 후 제거 — 데이터 비트 SCL 확인 생략
데이터 비트에서 SCL을 놓기만 하고 상승을 확인하지 않는 옵션(`BB_DATA_SCL_CHECK 0`)을 시험했다.
SCL이 HIGH에 닿기 전에 다시 내려가 **패널이 아무것도 받지 못했다**(화면 무변화). 옵션을 없앴다.

### 🐛 벤치마크 오류 집계
`i2cPlatform.errorCount()`는 50회를 넘으면 `recoverBus()`가 0으로 되돌려, 오류가 많을수록
적게 집계됐다. 리셋되지 않는 `bitBang.errorCount()`로 센다.

## [v1.0.12] — 2026-11-01

### 🐛 24시간제 첫 화면 날짜("...일")만 우측 정렬되지 않던 문제 수정

**증상**: 24시간제에서 첫 OLED가 날짜를 보여줄 때만 마지막 "일"이 시·분·초의 우측 고정
열(x=96)에 붙지 않고 왼쪽에 남아, 네 화면의 글자 끝이 어긋나 보였다.

**원인**: 제목 화면(첫 화면)을 무조건 가운데 정렬하는 `isCenteredText()` 규칙 때문에 날짜만
`layoutCharX(count, j, true)` 갈래를 탔다. 시·분·초는 비정렬 갈래에서 마지막 글자를 x=96에
붙이므로 날짜의 "일"만 어긋났다. 12시간제는 제목 화면에 "오전"/"오후" 라벨이 와서 문제가 없었다.

**수정**: 날짜 판정을 순수 모듈 `layoutIsDayText()`(UTF-8 접미사 "일", memcmp)로 떼어내고,
`isRightAlignedText()`가 "제목 화면 + 날짜"일 때만 우측 정렬 갈래를 고르게 했다.
`isCenteredText()`는 그 갈래를 먼저 배제한다 — 정적 경로(`drawCenterText`)·애니메이션
경로(`updateAll`)가 모두 이 함수를 거치므로 규칙이 한 곳에 남는다. 12시간제의 "오전"/"오후"는
라벨이므로 가운데 정렬을 유지한다. 웹 미리보기도 `isDayText()`/`isCenteredPreview()`로 같은
규칙을 미러한다. 본판 `Hangeul_Clock` v2.9.6과 동일한 수정이다.

**검증**: `test/test_layout.cpp` 24 passed / 0 failed(날짜 판정·우측 정렬 10건 신설),
`test/js/day_align_test.mjs` 20 passed / 0 failed 신설 → JS 전체 78 passed / 0 failed.
ESP32-C3(`esp32:esp32:makergo_c3_supermini`) 컴파일 통과.

## [v1.0.10] — 2026-10-21

### ✅ USB CDC Serial 비차단화 — 잠재 블로킹 제거

ESP32-C3 USB CDC(HWCDC)는 호스트가 포트를 읽지 않아 TX 링버퍼(256B)가 가득 차면
`HWCDC::write()`가 호출당 최대 2초(`tx_timeout_ms` 100 ms × `max_consec_timeouts` 20회)를
블로킹한다. 진단 로그 한 줄로 메인 루프(4버스 BitBang 전송·버튼)가 멈추지 않도록
`Serial.begin()` 직후 `Serial.setTxTimeoutMs(0)`을 적용했다. (`ARDUINO_USB_CDC_ON_BOOT` 가드)

### 🧹 쓸데없는 코드 정리

전송 계층이 캡처 후 재생으로 정착하면서 만들었다가 안 쓰게 된 코드를 전부 걷어냈다.

| 제거 | 왜 |
|:--|:--|
| `i2c_retry_policy.h` + 그 테스트 | dirty 마스크 장부를 안 쓰게 됨 |
| `preparePageUpdate` `pageIsDirty` `pageFirstTile` `pageTileCount` `pageMarkResult` `hasPendingHwUpdate` | 동시 경로가 **장부 없이** diff 결과를 바로 쓴다 |
| `_dirty[]` `_first_tile[][]` `_tile_count[][]` | 그 장부의 저장소 |
| **`bbPageCommand` `bbBuildPagePayloads`** | **우리가 명령 바이트를 만들지 않게 됐다** — 가장 많은 버그를 낳은 경로 |

| `HW_TASK_STACK/PRIO/CORE` | 워커 태스크 제거 (전송이 동기) |

**대신 `recoverBus()`를 살렸다.** 오류 누적 시 SCL 펄스로 버스를 풀어준다 —
BitBang은 stuck-low를 ACK 성공으로 오독할 수 있어 오류 카운터가 유일한 단서다.
호출자가 없어 죽은 코드가 될 뻔한 것을 **실제로 도달 가능한 안전망으로** 배선했다.

## [v1.0.8] — 2026-10-10

### ⚡ 비트 클럭 — `delayMicroseconds()`의 호출 오버헤드 제거

원본보다 느렸던 원인은 **비트 클럭**이었다.

| | 비트 클럭 |
|:--|:--|
| 원본 화면 0·1 | **800 kHz** (하드웨어 I2C + 백그라운드 태스크) |
| 원본 화면 2·3 | **사실상 최대** — SW I2C인데 **지연 콜백이 없었다** |
| 이 펌웨어 (v1.0.7까지) | **약 455 kHz** |

`delayMicroseconds(1)`은 **1us를 요청해도 호출 오버헤드로 실효 1.3us**가 된다.

**수정** — 부팅 시 **CPU 사이클을 실측**해 목표 ns에 맞춘 **NOP 루프**를 쓴다.
CPU 주파수를 런타임에 읽으므로 주파수가 달라져도 어긋나지 않는다.

| `BB_HALF_BIT_NS` | 비트 주기 | 실효 클럭 |
|--:|--:|--:|
| 2500 | 5.0us | 약 200 kHz |
| 1250 | 2.5us | 약 400 kHz |
| 600 | 1.2us | 약 833 kHz |
| 0 | 보정 안 함 | 최대 속도 |

## [v1.0.7] — 2026-10-10

### 🐛 "화면은 정상인데 느리다" — 동시 전송이 매번 실패해 순차 폴백으로 돌고 있었다

**인덱스 공간 불일치**가 원인이었다.

| 무엇 | 인덱스 공간 |
|:--|:--|
| `g_frameDirty[]` `g_pageFirst[][]` `screens[]` | **화면** |
| `_cap_buf[]` `replayCaptured(busMask)` `bitBang` | **버스** |

화면 순서를 뒤집으면서 `screens[0]`의 버스가 **3**이 되었는데,
화면 마스크를 그대로 버스 마스크로 넘겼다.

```
화면 0만 바뀜 → mask 0x01(화면) → 버스 0의 캡처 버퍼는 비어 있음 → 실패 → 순차 폴백
```

**4화면이 전부 바뀔 때만(0x0F) 두 공간이 우연히 일치**해 동시 전송이 됐다.
일상 갱신은 **항상** 실패했고, 캡처 오버헤드 + 순차 재전송이 겹쳐 **순차 단독보다 느렸다.**

**수정** — 마스크를 버스 공간으로 만든다: `busMask |= 1u << BB_BUS_OF_SCREEN(s)`.
폴백 판정도 버스 비트로 하고, 해당 **화면**을 순차 경로로 다시 보낸다.

### 🔎 폴백이 일어나면 시리얼로 알린다

동시 전송이 죽어 순차 폴백으로만 도는 상태는 **화면으로는 정상으로 보인다.**
다시 같은 함정에 빠지지 않도록 **처음 한 번** 알린다.

```
[I2C] 동시 재생 실패 -> 순차 폴백 (bus=0x08 ok=0x00) err=1
```

**이 줄이 안 보이면 동시 전송이 정상 동작 중**이다.

| C | U8g2 CAD 페이지별 (순차) | ✅ 정상 |

**B가 A와 같다는 것은 동시 전송 구현이 하드웨어에서 맞다는 뜻**이다.

### 🔍 v1.0.4는 왜 깨졌나 — dirty 장부 경유

진단 4의 B는 **diff 결과를 곧바로 캡처·재생**한다. v1.0.4는 `preparePageUpdate()` →
`pageFirstTile()/pageTileCount()`로 **장부를 거쳐** 같은 일을 했다.
코드 검토로는 같은 값이 나온다고 판단했지만 실기에서는 v1.0.4만 깨졌다.

→ **검증된 형태로 구현한다.** 장부를 거치지 않고 diff가 알려준 구간을 그대로 쓴다.

## [v1.0.2] — 2026-10-10

### 🔬 실기 진단 결과 — 하드웨어는 정상이었다

```
[진단 1] 4버스 모두 0x3C OK        → 배선·전원 정상
[진단 2] 4버스 모두 probe ACK      → 비트 타이밍·ACK 판독 정상
```

### 🐛 진단 3·4가 애초에 그릴 수 없는 상태였다 (진단 코드 자체의 버그)

`bitBang.begin()`은 핀을 Open-Drain + **출력 래치 1**로 잡는다. 그런데 Multi_BitBang은
`pinMode(OUTPUT)`만 하고 `digitalWrite()`를 하지 않아 **래치가 그대로 출력 레벨**이 된다 —
래치가 1이면 `SCL_LOW()`가 HIGH를 민다.

**"진단 3이 아무것도 못 그린다"를 하드웨어 문제로 오독해 한동안 엉뚱한 곳을 팠다.**

→ 단계마다 `claimPinsForMultiBitBang()` / `claimPinsForOwnDriver()`로 핀 소유권을 명시.

### ✨ 컨트롤러 스윕 — SH1106 / WINSTAR / SSD1315 / SSD1306

1.3" 모듈은 **겉모습도 주소도 같고 컨트롤러만 다르다.** I2C에 읽기 경로가 없어
**소프트웨어로 구별할 수 없다.** → 네 종류를 차례로 그려 보고 **사람이 고른다.**

**결과: SH1106 확정.** `OLED_DRIVER` 선택과 **SH1106 열 오프셋(+2)** 지원을 추가했다
(132열 RAM이라 가시 영역이 2열부터 시작).

## [v1.0.1] — 2026-10-10

### 🐛 화면에 노이즈만 나오던 문제 — 제어바이트 Co 비트

명령과 데이터를 **한 I2C 트랜잭션에 합쳐** 보낸 것이 원인이었다.

SSD13xx 제어바이트의 **Co 비트**가 `0`이면 "**이 제어바이트가 마지막**"이라는 뜻이라,
뒤따르는 `0x40`은 제어바이트가 아니라 **명령 `0x40`**(set display start line)으로 해석된다.
이어지는 픽셀 바이트가 전부 명령으로 먹혀 **GDDRAM이 한 번도 안 써진다.**

**왜 하필 "화면이 켜진 채 노이즈"였나** — 초기화는 U8g2가 각 명령을 별도 트랜잭션으로
보내므로 정상 동작한다. 그래서 charge pump와 display-on은 성공해 패널은 켜지고,
GDDRAM에는 전원 투입 시의 **랜덤 RAM**이 남았다. ACK는 정상이라 **오류가 안 보였다.**

**수정** — 명령과 데이터를 **분리된 두 트랜잭션**으로.
규칙을 순수 함수로 옮겨 회귀 테스트 8건을 추가했다.

### 🛡️ 함께 고친 것

- **한 버스 고장이 4화면 정지** → 동시 전송 실패 시 **버스별 재시도**
- **WiFi 설정 화면 경합** — `configModeCallback`이 `sendBuffer()`로 버스를 직접 몰아
  워커 태스크와 충돌 → `pushParallel()`로 교체

## [v1.0.0] — 2026-10-10

`Hangeul_Clock` **v2.9.3**을 복사해 전송 계층만 BitBang I2C로 교체한 첫 릴리스.

### 1. 4× 1.3" OLED를 위한 4버스 BitBang

1.3" 모듈은 주소를 바꿀 수 없어(전부 0x3C) 버스가 4개 필요하다.
**SCL 1개(GPIO 10)를 공유**하고 **SDA만 4개(GPIO 5/6/7/8)** 로 나눈다.

**핵심**: I2C 슬레이브는 SCL 상승 에지에서 자기 SDA만 래치하므로, SCL을 공유한 채
4개 SDA에 **서로 다른 비트를 동시에** 실으면 4화면이 각자 자기 바이트를 동시에 받는다.
ACK도 한 클럭에 4개를 모두 읽는다.

| 방식 | 4화면 풀 프레임 |
|:--|--:|
| 순차 BitBang | 약 80~110 ms |
| **동시 BitBang** | **약 15~30 ms** |

### 2. 전송 계층 단일화

원본의 "HW I2C 2화면 + SW I2C 2화면" 이원화를 제거하고 4화면 모두 dirty 페이지
경로로 통일했다. ESP-IDF `i2c_master` 의존을 걷어내 **Flash 7.7 KB 감소**.

### 3. 핀맵 개편

| 신호 | 변경 |
|:--|:--|
| SCL | GPIO 10 (4버스 공유) — 신규 |
| SDA | GPIO 5 / 6 / 7 / 8 — 신규 |
| BTN1~4 | 1/4/10/9 → **0/1/3/4** |
| 부저 | GPIO 7 → **제거** (GPIO 7은 이제 OLED3 SDA) |

### 4. 그 밖에

- `HAS_BUZZER 0` — 부저 미연결, 완전 무음 (복구 경로는 `#error`로 안내)
- AP 이름 `Hangeul_Clock_BB` (원본 기기와 구분)
- 부팅 시 내장 Multi_BitBang으로 **4버스 스캔** — 배선 문제인지 코드 문제인지 먼저 가른다
- **Multi_BitBang 벤더링** (GPLv3, 원본 무수정) — 사유는 [`VENDORED.md`](./VENDORED.md)
- **Multi_OLED 미채택** — SSD1315 미지원 + 폰트 3종 고정이라 커스텀 64px 한글 글리프와
  Font Studio를 소화하지 못한다. 렌더링은 U8g2를 유지했다.
